# Megashoppee marketplace platform

GitHub-ready monorepo foundation for the Megashoppee multi-vendor marketplace.

This document is the full local install, database connection, and run guide.

## Applications

| Folder | Role | Production host | Local URL |
|--------|------|-----------------|-----------|
| `apps/storefront` | Customer marketplace | `megashoppee.com` | http://localhost:5173 |
| `apps/vendor` | Vendor portal | `vendor.megashoppee.com` | http://localhost:5174 |
| `apps/admin` | Admin console | `admin.megashoppee.com` | http://localhost:5175 |
| `apps/api` | NestJS REST API (backend) | API host | http://localhost:4000/api/v1 |
| `packages/shared` | Shared contracts and utilities | — | library only |

## Stack

React + TypeScript + Vite, Tailwind CSS, NestJS, MySQL 8, Prisma, pnpm workspaces.

**No Docker** in this package. MySQL runs as a normal Windows/Linux service. MySQL Workbench is the GUI to view data and run the one-time setup SQL.

## How the pieces connect

Websites never talk to MySQL. Only the API does.

```text
Browser
  │
  │  storefront :5173
  │  vendor     :5174
  │  admin      :5175
  │
  │  each uses VITE_API_BASE_URL
  ▼
API (NestJS)  :4000
  │
  │  apps/api/.env  →  DATABASE_URL
  ▼
MySQL Server  127.0.0.1:3306
  database: megashoppee
  user:     megashoppee_app
```

| Link | Config file | Setting |
|------|-------------|---------|
| Frontend → backend | `apps/storefront/.env`, `apps/vendor/.env`, `apps/admin/.env` | `VITE_API_BASE_URL=http://localhost:4000/api/v1` |
| Backend → MySQL | `apps/api/.env` | `DATABASE_URL=mysql://megashoppee_app:PASSWORD@127.0.0.1:3306/megashoppee` |
| Create MySQL database + user (once) | `database/mysql-workbench-setup.sql` | Same username and password as `DATABASE_URL` |
| Admin API gate (not MySQL) | `apps/api/.env` | `ADMIN_API_KEY` (admin UI sends header `x-admin-api-key`) |

MySQL Workbench is **not** the app connection. It is only a viewer. The running project always uses `apps/api/.env`.

## Package installation and database connection

These steps are independent. Package installation prepares Node.js libraries. Database connection is how the API authenticates to MySQL. One does not replace the other.

All `pnpm` commands below must be run from the `megashoppee` project folder.

### 1. Package installation

```bash
pnpm install
```

Downloads application libraries (React, NestJS, Prisma, and related packages) into `node_modules`.

| This command | |
|--------------|--|
| Connects to MySQL | No |
| Creates the `megashoppee` database | No |
| Creates tables | No |
| Reads a database password | No |

After this step, the project can compile and start, but it still has no MySQL login until `DATABASE_URL` is configured and the database exists.

### 2. Database connection

The API is the only process that connects to MySQL. Frontends call the API; they never use `DATABASE_URL`.

MySQL Workbench is a client for inspecting data. It is not the application connection. The running API always reads `apps/api/.env`.

#### Connection string

**File:** `apps/api/.env` (copy from `apps/api/.env.example`)

```env
DATABASE_URL="mysql://megashoppee_app:YOUR_PASSWORD@127.0.0.1:3306/megashoppee"
```

| Segment | Meaning |
|---------|---------|
| `mysql://` | Protocol (Prisma MySQL URL) |
| `megashoppee_app` | MySQL username |
| `YOUR_PASSWORD` | MySQL password |
| `127.0.0.1:3306` | Host and port of the local MySQL Server |
| `megashoppee` | Database name |

The variable name `DATABASE_URL` is required by Prisma (`apps/api/prisma/schema.prisma` uses `url = env("DATABASE_URL")`). The sample values are defined in this repository so they match `database/mysql-workbench-setup.sql`. The URL is not generated by MySQL or Workbench.

#### Prerequisites on the MySQL server

Before the URL can succeed, MySQL must already contain that database and user. Create them once by executing `database/mysql-workbench-setup.sql` in Workbench (account with `CREATE DATABASE` / `CREATE USER`, typically `root`).

The password in the SQL script and in `DATABASE_URL` must be identical.

#### Apply schema and run

```bash
pnpm db:push
```

Reads `DATABASE_URL`, connects to MySQL, and creates or updates tables.

```bash
pnpm dev
```

Starts the websites and the API. The API reads the same `DATABASE_URL` on startup and keeps the connection open so storefront, vendor, and admin can load data.

### Comparison

| | Package installation | Database connection |
|--|----------------------|---------------------|
| Mechanism | `pnpm install` | `apps/api/.env` → `DATABASE_URL` |
| Requires MySQL | No | Yes |
| Result | Libraries in `node_modules` | API can read and write database `megashoppee` |
| Creates tables | No | Yes, after `pnpm db:push` |
| Used at runtime | Yes (Node loads those libraries) | Yes (API connects on start) |

Recommended sequence:

```text
pnpm install       →  packages only (no database)
pnpm db:generate   →  generate Prisma client
pnpm db:push       →  connect and create tables
pnpm dev           →  run the app (API remains connected)
```

### Changing the database name

The database name is the last segment of `DATABASE_URL` (currently `megashoppee`). To use a different name:

1. Create that database in MySQL and grant privileges to `megashoppee_app` (update `database/mysql-workbench-setup.sql` if you re-run setup).
2. Set the same name at the end of `DATABASE_URL` in `apps/api/.env`.
3. Run `pnpm db:push` and restart `pnpm dev`.

The project folder name, frontend `VITE_API_BASE_URL` values, and Prisma model names do not need to change. MySQL does not rename an existing database automatically; create the new database (and migrate data if required), then point `DATABASE_URL` at it.

## Phase 1 — Install and database setup (one time)

### 1. Create the MySQL database and user (Workbench)

The project does **not** create the MySQL database by itself. You (or an installer) must run the setup script **once** against a running MySQL Server.

1. Open **MySQL Workbench**.
2. Connect to **Local instance MySQL80** (or your local MySQL connection) with an account that can `CREATE DATABASE` and `CREATE USER` (usually `root`).
3. **File → Open SQL Script**.
4. Open `database/mysql-workbench-setup.sql`.
5. Choose one development password. Replace every `'ChangeThisStrongPassword'` in the script with that password, **or** keep the default and use the same string in `.env`.
6. Execute the **entire** script (lightning bolt).
7. Refresh **Schemas**. You should see database **`megashoppee`**.

That script creates:

- database `megashoppee`
- user `megashoppee_app`@`localhost` and `@127.0.0.1`

It does **not** create application tables. Tables come from Prisma in step 4.

Workbench details: see `database/README.md`.

### 2. Environment files (the connection keys)

Copy templates if `.env` files do not exist:

| Copy from | Copy to |
|-----------|---------|
| `.env.example` or `apps/api/.env.example` | `apps/api/.env` |
| `apps/storefront/.env.example` | `apps/storefront/.env` |
| `apps/vendor/.env.example` | `apps/vendor/.env` |
| `apps/admin/.env.example` | `apps/admin/.env` |

**Backend ↔ database** — `apps/api/.env`:

```env
DATABASE_URL="mysql://megashoppee_app:ChangeThisStrongPassword@127.0.0.1:3306/megashoppee"
API_PORT=4000
CORS_ORIGIN="http://localhost:5173,http://localhost:5174,http://localhost:5175"
ADMIN_API_KEY="replace-this-with-a-long-random-development-secret"
```

The password in `DATABASE_URL` **must match** the password in `mysql-workbench-setup.sql`.

**Websites ↔ backend** — each frontend `.env`:

```env
VITE_API_BASE_URL=http://localhost:4000/api/v1
```

Do not put `DATABASE_URL` in the frontend apps. They only call the API.

### 3. Install packages

From the `megashoppee` folder:

```bash
pnpm install
```

This downloads libraries only. It does **not** connect to MySQL.

### 4. Create tables (this is the first Prisma database connection)

```bash
pnpm db:generate
pnpm db:push
```

| Command | Connects to MySQL? | What it does |
|---------|--------------------|--------------|
| `pnpm install` | No | Downloads packages |
| `pnpm db:generate` | No (reads `.env` for Prisma) | Generates Prisma client |
| `pnpm db:push` | **Yes** | Uses `DATABASE_URL`, creates/updates tables in `megashoppee` |
| `pnpm db:seed` | **Yes** | Optional sample rows |
| `pnpm db:studio` | **Yes** | Browser UI for tables |

After `db:push`, Workbench → **Schemas → megashoppee → Tables** should list tables such as `customer`, `vendor`, `product`, `order`, `category`, and others defined in `apps/api/prisma/schema.prisma`.

This package uses **`pnpm db:push`** for local development (schema file is the source of truth). Do not use `db push` as the production migration strategy. For production, generate and review Prisma migrations, then `prisma migrate deploy`. See `apps/api/prisma/migrations/README.md`.

Optional sample data:

```bash
pnpm db:seed
```

## Phase 2 — Run the project (every work session)

From the `megashoppee` folder:

```bash
pnpm dev
```

Leave that terminal open. **Ctrl+C** stops everything.

`pnpm dev` starts four processes:

| Process | Port | Database? |
|---------|------|-----------|
| Storefront | 5173 | No — calls API |
| Vendor | 5174 | No — calls API |
| Admin | 5175 | No — calls API |
| API | 4000 | **Yes** — on startup Prisma `$connect()` using `DATABASE_URL` |

### Prove it works

1. **Backend ↔ MySQL:** open http://localhost:4000/api/v1/health  
   Expect JSON including `"database":"connected"`.
2. **Frontend:** http://localhost:5173 (vendor 5174, admin 5175).
3. **Tables:** Workbench → `megashoppee` → Tables, or:

```bash
pnpm db:studio
```

If health fails or the API exits immediately: MySQL service not running, wrong password, or `megashoppee` database/user never created.

## Where the database connection is in code

You do **not** paste the MySQL password into TypeScript.

1. `apps/api/.env` sets `DATABASE_URL`.
2. `apps/api/prisma/schema.prisma` uses `url = env("DATABASE_URL")`.
3. NestJS `ConfigModule.forRoot()` loads `.env` (`apps/api/src/modules/app.module.ts`).
4. `PrismaService` calls `$connect()` on API start (`apps/api/src/modules/prisma.service.ts`).

Frontends use `import.meta.env.VITE_API_BASE_URL` (see `apps/*/src/api.ts`).

## Common mistakes

| Symptom | Cause | Fix |
|---------|--------|-----|
| `Command "db:studio" not found` / `db:push` not found | Terminal is in the **parent** folder | `cd` into `megashoppee` |
| Access denied / unknown auth plugin | User not created or password mismatch | Run setup SQL; match `DATABASE_URL` |
| Health `ERR_CONNECTION_REFUSED` on :4000 | API not running or crashed | `pnpm dev`; check MySQL80 is Running |
| No tables under `megashoppee` | `db:push` not run | `pnpm db:push` from `megashoppee` |
| Looking at `cafe_pos` / `goatball_db` | Wrong schema | Use schema **`megashoppee`** |
| Websites load but no data | API down or empty tables | Health URL; optional `pnpm db:seed` |

## Important implementation status

This repository is a structured, runnable foundation, not a finished production marketplace. It includes app shells, shared design tokens, an initial relational schema and API module boundaries. Payment marketplace routing, WhatsApp OTP provider, email delivery, object storage, tax/invoice rules, shipping carrier integrations, refunds and payout operations require provider credentials, formal business rules and end-to-end testing before production. The mock OTP mode is development-only. Never enable it in production.

## Business rules encoded in the design

- One customer checkout creates a parent order and vendor suborders.
- Customer login is mobile + WhatsApp OTP; no guest checkout.
- Vendor and product approvals are admin-controlled.
- Vendor-specific commission overrides category-specific, which overrides global.
- Commission base is discounted product value excluding shipping and tax.
- No COD at launch.
- Vendors cannot initiate withdrawals. Admin reviews and initiates payouts.
- Customer support is centrally managed; vendors cannot privately message customers.
- Vendor contact details are private.
- All sensitive financial and administrative actions must be audited.

## Production checklist

- Configure a compliant marketplace payment/fund-flow arrangement with Razorpay (including Route/linked-account eligibility as applicable).
- Configure approved WhatsApp Business OTP templates and delivery provider.
- Configure SMTP/email and object storage.
- Add rate limiting, monitoring, backups and restore drills.
- Complete security review, accessibility testing and load testing.
- Have an Indian CA/legal professional validate GST, invoicing, consumer protection and marketplace obligations.
- Replace development-only placeholders and write integration/e2e tests before launch.
- Generate and commit reviewed Prisma migrations; do not use `db push` in production.

## Deployment

Build each app separately and deploy behind the relevant subdomain. Deploy the NestJS API as a Node application. Configure HTTPS, environment variables, MySQL network access and reverse proxy/API URL. Keep secrets out of Git (never commit `.env`).
